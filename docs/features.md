# Features

This page describes everything L1 Data does. The [README](../README.md) has the short version.

## Connections and the catalog

- **Explore database map** in a table's sidebar menu opens a resizable dock beside SQL and results. Follow incoming and outgoing declared foreign keys, inspect ordered column pairs, expand neighbors, drag tables, pan, zoom, and fit the map. **Active query** overlays conservative analysis of the cursor statement. Select a table, source occurrence, or supported SQL equality to highlight its source without changing or running SQL. Bare-name matches are labeled tentative, and unsupported syntax reports partial analysis. The map stays in its original database and resets after a catalog refresh or disconnect. Exploration pages 32 constraints at a time and stops explicitly at 160 tables or 512 relationships.

![Orders and its incoming and outgoing relationships, with a query join highlighted in SQL](images/database-map.png)

- Choose PostgreSQL or SQL Server when creating a connection. Each tab loads that connection's SQL dialect for highlighting, completion, formatting, and execution. SQL Server connects over TCP with a SQL login or with **Microsoft Entra ID (Azure CLI)**, chosen under **Authentication**. Its defaults are port 1433 and database `master`. To change database kind, create a new connection. Existing saved connections keep PostgreSQL.
- **Microsoft Entra ID (Azure CLI)** signs in to Azure SQL as the account of `az login`. The engine runs `az account get-access-token` and keeps the token in memory until five minutes before it expires, so the tabs of a connection share one `az` call. No password or Azure credential is saved. Install the [Azure CLI](https://learn.microsoft.com/cli/azure/install-azure-cli) and run `az login` first. If the server refuses the token, the next try asks `az` again, so running `az login` with another account takes effect at once. A pasted `sqlserver://` URL with `Authentication=ActiveDirectoryAzCli`, as a query option or a `;key=value` property, selects it.
- The connection tree shows each connection's databases, their schemas with their table counts, the tables and views of each schema, and a Functions group. Sequences, Types, and Synonyms follow Functions when the schema has any. Extensions follow the schemas when the database has any. An empty group stays hidden. Expand a table to see Columns, with a type glyph, primary and foreign key marks, the type, and `· null` on nullable columns. Defaults, Keys (primary, foreign with its target, unique, and check), Indexes (key list, method, and partial predicate), and Triggers (timing, events, and implementation) follow when the table has any. Use the arrow keys to move through the tree. `→` opens a row or moves into it, `←` closes it or moves to its parent, `Home` and `End` jump to the first and last rows, and `Enter` opens a table or view, inserts a routine, or opens and closes any other row. Type the start of a name to jump to the next row that begins with it.
- A connection row's `shown/total` count opens a picker of the server's databases, and a database row's count opens a picker of its schemas. Check a box to show that database or schema in the tree, or use **All**, **Default only**, or **None**. Adding a database also shows its default schema. System databases and schemas stay out of the pickers until you turn on **Show system databases** or **Show system schemas**. The count turns amber when nothing is shown. Each connection keeps its choices. The picker opens with its filter focused, `Tab` cycles inside it, and `Esc` or **Done** closes it and returns focus to the count.
- A disconnected connection row shows a **Connect** button in place of its count; a connected row shows only the count, dimmed while it is off.
- Double-click a table or a view to browse its rows in a tab. Saved PostgreSQL browse tabs keep paging, filters, sorting and editing with a trailing semicolon or outer whitespace in their generated query. Double-click a routine to insert its template at the active tab's cursor. The tab must target a saved connection of the same database kind. An unresolved or mismatched target shows an error without editing or retargeting the tab. SQL Server functions insert schema-qualified expressions for `SELECT` or `FROM`, and procedures insert `EXEC` calls. Templates with parameters require argument values. Replace the editable `NULL` placeholders as needed, declare table-valued arguments as `@table_argument_N` variables, and use variables with `OUTPUT` to capture output parameters.
- Right-click a table, a view, a sequence, a type, a synonym, or an extension and choose **Script as CREATE**, or right-click a routine, an index, or a trigger and choose **Open source**. A new tab opens on the object's database, titled with its name, holding the DDL that creates it. The names L1 Data writes carry their schema, and so do the names PostgreSQL prints in expressions and in view, index, constraint, and trigger definitions. A routine body and a SQL Server module's text stay as the database stored them, except that a SQL Server module's `CREATE` header, and a trigger's `ON` table, name the object's current schema and name. **Open source** on an index that backs a primary key or a unique constraint opens the `ALTER TABLE ... ADD CONSTRAINT` that creates it, and on a PostgreSQL partition's attached index it adds the `ALTER INDEX ... ATTACH PARTITION` to its parent index. The script covers a fixed list of property kinds. It writes each kind in the first list below, and when the object has a kind in the second list, `-- L1 Data could not script:` lines at the top of the script name it and a toast repeats them. A kind in neither list is not covered. A PostgreSQL partition script gives each attached index its source name back; if an index the script did not create already holds that name where it runs, the script leaves that index alone, names its own copy `l1_<oid>`, and raises a `WARNING`.
  - PostgreSQL, written: columns with type, collation, identity and its sequence options, `serial`, generated expressions, defaults, and `NOT NULL`; primary key, unique, foreign key, check, and exclusion constraints, `NOT VALID` included, with a foreign key between tables of one partition tree added after the whole tree, with a key's index storage parameters and tablespace; indexes with their tablespace, clustering, replica identity, and column statistics targets; triggers and rules with their enabled state; row-level security and policies; replica identity; table and TOAST storage parameters, `UNLOGGED`, access method, and tablespace; column storage, compression, statistics, and options; owned sequences with their comments and `UNLOGGED`; extended statistics; comments on the object and each of its parts; inheritance parents; typed tables; the whole partition tree with what each partition sets differently from its parent, including cloned trigger states and attached index names, storage parameters, and tablespaces; foreign tables and their options; view options and check options; materialized view population; and a routine's `DEPENDS ON EXTENSION`. A sequence's type and the options that differ from the defaults, its `OWNED BY` column, its `UNLOGGED` state, and its comment. An enum's labels in order, and its comment. A domain's base type, collation, default, `NOT NULL`, and check constraints, and its comment. A composite's fields with type and collation, and its comment. A range's subtype, a non-default subtype operator class, collation, canonical function, and subtype diff, and its comment. An extension's schema and version, and its comment.
  - PostgreSQL, warned: privileges, listed one change at a time; the owner, when it differs from the connecting role, and always for a `SECURITY DEFINER` function, a view, or a materialized view; security labels on the relation, its columns, its sequences, or a routine; publication membership, directly or through `FOR TABLES IN SCHEMA`; an invalid index; a partitioned index not attached to every partition; and an inheritance child's column order or generation expression that a replay cannot keep. Privileges on a sequence or a type, listed one change at a time. The owner of a sequence, a type, or an extension, when it differs from the connecting role. Security labels on a sequence, a type, or an extension.
  - SQL Server, written: columns with identity, computed, sparse, column set, masked, and row GUID settings, system-versioning period columns (`GENERATED ALWAYS AS ROW START` and `ROW END`), `GENERATED ALWAYS AS TRANSACTION_ID` and `SEQUENCE_NUMBER` columns, `HIDDEN`, collation, and named defaults; keys, foreign keys, and checks with their options and disabled, untrusted, and not-for-replication states; rowstore and columnstore indexes with their options, and disabled indexes; heap compression and lock escalation; system versioning; triggers with their state and First and Last order; string extended properties; sensitivity classifications; change tracking, which the script enables only where the database has change tracking on and otherwise reports with `PRINT`; `text in row` and `large value types out of row`; user statistics with their columns, filter, `NORECOMPUTE`, and `AUTO_DROP`; bound defaults and rules this login can see; and each module under its `SET ANSI_NULLS` and `SET QUOTED_IDENTIFIER` lines. A sequence's type, start, increment, minimum, maximum, cycle, and cache size. A default cache, which SQL Server stores without a size, is left out. An alias type's base type with length, precision, and scale, and `NULL` or `NOT NULL`. A table type's columns with type and nullability. A synonym's stored base object name.
  - SQL Server, warned: privileges, listed one change at a time, and a note when the login cannot see them all or every classification; an owner set by `ALTER AUTHORIZATION` that differs from the schema's owner, and the owner an `EXECUTE AS OWNER` module runs as; filegroups and partition schemes; XML, spatial, hash, full-text, and hypothetical indexes; `STATISTICS_INCREMENTAL`, `SUPPRESS_DUP_KEY_MESSAGES`, and compression that differs by partition; incremental and persisted-sample statistics; FILESTREAM, `ANSI_PADDING OFF`, and Always Encrypted columns, and any other `GENERATED ALWAYS` kind; non-string extended properties; a history table's role; CLR and encrypted triggers; definitions SQL Server hides from a login without VIEW DEFINITION, and a bound default or rule it cannot see; the current name in a module's `CREATE` header, when the header cannot be read; change data capture; numbered procedures after the first; and module signatures. Privileges on a sequence, a synonym, or a type, listed one change at a time, and a note when the login cannot see them all. An owner set by `ALTER AUTHORIZATION` that differs from the schema's owner, for a sequence, a synonym, or a type. A table type column's default, identity, computed value, or key.
  - Aggregates, SQL Server memory-optimized, ledger, graph, external, and FileTable tables, and CLR or encrypted modules cannot be scripted yet, and say so. A built-in or pseudo type cannot be scripted, and says so.
- `⌘P` opens quick navigation from the workspace or Settings. Search databases, open query, file and table tabs, and tables and views from loaded catalogs by name or connection, database and schema context. File tabs also match their paths. Hidden databases remain searchable. Use `↑` and `↓`, then `Enter` to open a destination, or `Esc` to cancel. Choosing a database reuses an existing SQL tab there, preferring the active tab, or opens a new query without changing any existing session.
- `⌘⇧P` opens a searchable command panel from the workspace or Settings. Search available workspace commands by name, use `↑` and `↓` to select one, and press `Enter` to run it. Each command shows its keyboard shortcut. `Esc` returns to the previous control and keeps the Settings filter. Pending questions and other dialogs stay open when you press the shortcut.
- The sidebar's always-visible search field filters the tree in place. It has no visible background or border at rest, a background on hover, and a background with an accent border when focused. The tree keeps the tables, views, columns, functions, sequences, types, synonyms, and extensions whose names contain every word you type, in the schemas it shows, and opens each match's parents and highlights the match. It matches those names, not an enum's labels, a composite's fields, or a synonym's target. A matching column sits under its table. `Enter` opens the first table or view whose name starts with the words you typed, else the first one listed. `Esc` clears the search. `↓` moves into the tree.
- The connection dialog lists the saved connections on the left, with a live dot on each connected one. Click one to edit it, or **New** to add another. Paste a `postgres://` or `sqlserver://` URL to fill in the database kind, server, database, user, password, and TLS mode. The name is optional and defaults to the host and database. Pick a color to mark the connection in the tree and the top bar. To shade each colored connection in the tree with its color instead of a dot, turn on **Tint connections by color** in **Settings** > **Appearance**. **Test** shows the server version before you save. Leaving a form with unsaved edits, by choosing another connection or closing the dialog, asks before it drops them. Right-clicking a connection connects, disconnects, opens a SQL tab, refreshes the catalog, edits, and deletes.
- Set **Environment** in the connection dialog to **Develop**, **Staging**, or **Production**, or leave it **Not set**. You can change it later. The **Run** button is yellow for Staging, red for Production, and blue otherwise. The connection tree shows a database icon before the connection name, blue for Develop, amber for Staging, red for Production, and muted when not set.
- **Run**, **Explain**, and **Explain Analyze** ask for PostgreSQL `:name` or `$1` parameters and undeclared SQL Server `@name` variables before execution. Repeated names share a value. Values are text or **NULL**, and Rust quotes them as literals. Each tab remembers accepted values until it closes or changes database. SQL Server parameter names match exact case, references to declared variables stay in SQL regardless of case, and procedure, function, trigger, or rule definitions do not prompt. Query history records the SQL that ran, with its values.
- On a Production connection, a run that writes asks first, for example **Run 2 writes on Production?**, names the connection and database, and shows the first three write statements. **Cancel** runs nothing. The question counts only the statements, or SQL Server batches, that the run executes: the selection, the marked statement, or all of them. A write is any statement that **Query history** puts under **Writes**, such as `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `TRUNCATE`, DDL, `GRANT`, `CALL`, `DO`, `EXECUTE`, `PREPARE TRANSACTION`, and `COMMIT PREPARED`. PostgreSQL `COPY ... FROM` counts too, including server-side files and `PROGRAM`. A `COPY ... TO` of a table or a read-only query does not count. A wrapped query uses the same write classification as an ordinary query. On SQL Server, a batch that writes or runs `EXEC` counts. On PostgreSQL every other query, including `COPY ... TO`, runs read-only, so a `SELECT` that writes through a function, `nextval`, or `SELECT ... INTO` fails and changes nothing. The log then says the statement tried to write, and running the same text again in that tab asks first. Outside a transaction, a read-only query keeps the session settings it changes. Inside one, it runs in a savepoint that is rolled back, so an error or **Cancel** leaves the transaction as it was, and a `set_config` the query made is undone. `SELECT ... FOR UPDATE` fails the same way and asks on the next run. On SQL Server the check reads only the SQL text, so a `SELECT` that calls a function with side effects runs without asking. Loading a table page asks only in the case below. **Submit** for staged edits asks too, for example **Apply 2 changes on Production?**, and counts the inserts, updates, and deletes it would send. The engine makes this check where the run starts, so a write that skips the question is refused too. An answer covers only the statements, connection, database, schema, mode, and transaction state it named. If any of them changes, the app asks again. A tab that connected while its connection was Production keeps asking after you change the environment, until its session closes, for example when you disconnect. When writes ran before the connection was marked Production and the app has not seen their transaction end, every run asks first and lists them, because any statement can commit them, and so does **Commit**, as **Commit on Production?**. Once you confirm, the app does not ask again for those writes.
- Turn on **SSH tunnel** in the connection dialog to reach the database through an SSH server. Sign in with a password, a private key file with an optional passphrase, or an SSH agent at `SSH_AUTH_SOCK` or a socket you name. The SSH server resolves and dials the database host, so a name only it knows, such as `db.internal`, works. The connection list shows the server after `via`. The app checks the server's host key against `~/.ssh/known_hosts`, which it never writes, and against its own `known_hosts` file in its data folder. When the key is unknown, **Test** shows its fingerprint with **Trust and test again**, and **Connect** asks before it trusts it. Trusting adds that key to the app's own file. A changed or revoked key fails, and the error says how to fix it. `~/.ssh/config` is not read, so enter the host, port, user, and key file in the dialog.
- The OS credential store holds one master key, and saved passwords and SSH secrets are sealed under it. macOS asks for keychain access once per launch.

## Query tabs

- With no tabs open, **Your SQL workspace** offers the existing query, file, connection, search, saved query, and settings actions. The list scrolls when the editor is short.
- The selected tab has an outlined pill. Focus it with `Tab`, then use `←` and `→` to switch tabs, wrapping at either end, or `Home` and `End` to jump to the first and last tabs. `Enter` or `Space` activates a focused tab. Tab to its close button and press `Enter` to close it. Focus moves to the selected neighbor, or **New query tab** after the last tab closes. File and transaction indicators stay visible beside the close button.

![SQL Server and PostgreSQL connections with a T-SQL batch and multiple result sets](images/sql-server.png)

- SQL Server tabs run T-SQL batches separated by a standalone `GO` line. Semicolons inside a batch keep their variable and temporary-table scope. A cursor runs its batch; a selection runs exactly the selected text. Several `SELECT` statements in one batch produce separate results. `GO` repetition counts and sqlcmd directives are unsupported. Choose a database in the app instead of issuing `USE`.
- Cancelling SQL Server resets the tab's session, including its temporary tables and open transaction. Earlier auto-committed writes remain committed. The toolbar shows **session reset**; an interrupted native transaction can have an unknown outcome.
- **Output** shows SQL Server `PRINT` and `RAISERROR` messages at severity 10 or lower as they arrive, in order with each result's row count and every error, as SSMS shows them. A result that an error cuts short shows as failed. A severity from 1 to 9 shows as a WARNING and turns the **Output** button amber. Each `INSERT`, `UPDATE`, `DELETE`, `MERGE`, or `SELECT INTO` logs its count, as "5 rows affected", and the results header shows the last one. A batch that counts no rows, such as one under `SET NOCOUNT ON`, logs "Commands completed successfully".
- Every tab is a query editor. A tab opened from a table also browses that table. Completion knows the clause at the cursor. After `FROM` or `JOIN` it lists tables, views, and CTEs. In a select list, `WHERE`, `ON`, or `SET` it lists the columns of the tables in scope, the database's functions with their arguments, and the dialect's built-in functions, such as `date_trunc` or `DATEADD`. After a table alias such as `o.` it lists that table's columns, also inside a subquery or for a CTE. Elsewhere it lists the keywords that can come next. Right after a table that can take an alias, two or more letters of a keyword that can follow, such as `wh`, list the keywords, but the word as typed comes first, so `Enter` keeps it as the table's alias. The arrow keys pick a keyword. In a file over one million characters, the list waits for a short pause in typing, because each request sends the whole file. Right after the `ON` of a join, the first entry is the join condition from the foreign keys between the joined table and the others in scope, such as `c.id = o.customer_id`, with every column of a composite key joined by `AND`. Nothing opens inside a string or a comment. The editor draws a rounded box behind the statement `⌘↵` will run. On PostgreSQL, a statement ends at `;`, or at a blank line when the next line starts a new statement. `⌘↵` or **Run** runs the selection as written, or the marked statement when nothing is selected. On a blank line nothing is marked, and `⌘↵` opens a list of the tab's statements instead. `⌘⇧↵` opens the list whenever the tab holds several statements. The list has an **All** row when there are several, and highlights in the editor what the row under the pointer or the arrow keys would run. `Enter`, a click, or a statement's number runs it and moves the cursor to its end. `Esc` closes the list. `Esc` or **Cancel** stops a running query.
- A PostgreSQL query tab can Explain and Explain Analyze one statement from the Run menu (`⌘⌥↵`, `⌘⌥⇧↵`). Explain Analyze on Production asks first, and the question says a rollback does not undo sequence values or outside side effects. The plan opens as a tree. The rows view is the JSON cell. Copy and a loaded JSON export read that cell. Export all is refused.
- A SQL Server query tab can Explain and Explain Analyze one batch from the same menu. Several batches separated by `GO` are refused. Explain sends the batch with showplan on and does not run it, including on Production, and it does not clear writes the tab already holds. Explain Analyze runs the batch. A batch that may write, begin a transaction, or read another server asks first, on every environment. Off Production the question is **Run this batch?** and says this app does not roll the batch back. The plan opens as a tree, with each statement above its own tree. The rows view is the showplan XML. Copy and a loaded export read that cell. Export all is refused. Cancelling Explain Analyze resets the session, the same as cancelling any SQL Server run.
- On PostgreSQL, `⌘⌥L` or **Format** formats the marked statement, or every statement the selection touches. Each clause starts a line, each list item and each `AND` or `OR` of a condition gets its own line, subqueries indent, and keywords are uppercase. Strings, comments, and function bodies stay byte for byte, and a column named like a keyword, such as `day`, keeps its case. Statements other than queries, `INSERT`, `UPDATE`, `DELETE`, and `CREATE TABLE` change only their keyword case. One `⌘Z` undoes the format. When the result might not mean the same, the editor keeps the text and says so.
- SQL Server formatting supports simple `SELECT`, `INSERT ... VALUES`, `INSERT ... SELECT`, `UPDATE`, and `DELETE` batches, with semicolons between statements. Other constructs stay unchanged and show an unsupported message. Advanced table filters and sort expressions accept a conservative expression subset. Use a query tab for subqueries, casts, `CASE`, `COLLATE`, or functions outside that subset.
- Each tab has its own session, so `SET` and temp tables stay with the tab. The top bar shows where the tab runs: the environment icon and the connection, then the database. Click the connection name to pick the tab's connection, or the database name to pick one of the databases the tree shows. When the bar is narrow, the database name shortens before the connection name. Below a 900-pixel bar **Format** shows only its icon, and below 520 pixels it hides. `⌘⌥L` still formats. On PostgreSQL, the **Auto-commit** menu also offers app-managed Manual mode. The menu shows a confirmed PostgreSQL rollback or a SQL Server session reset after connection loss. Double-click a tab to rename it, unless it is bound to a file.
- **Commit** and **Rollback** appear while a transaction is open. The tab shows an amber dot, and the mode menu shows **in transaction** in amber. When the transaction is aborted, the dot turns red and the menu shows **aborted** in red. Closing that tab or disconnecting asks before it rolls back.
- `⌘O` opens `.sql` files, several at once, each in a new tab on the database `⌘T` would use. A file that is already open switches to its tab. Files must be UTF-8 and at most 4 MB. The editor shows neither a byte-order mark nor CRLF line breaks, and a save writes back the ones the file had.
- `⌘S` saves the tab to its file. In a tab with no file, `⌘S` asks where to save it, as **Save As** (`⌘⇧S`) does, and binds the tab to the new file. A tab bound to a file is named after the file, and a ring beside the name shows while its text differs from the file. With pending table edits in the tab, `⌘S` submits them instead.
- A save writes a new file beside the old one and renames it over the old one, so a crash never leaves half a file. A crash during a save can leave a hidden `.<name>.*.l1data-tmp` file in the folder. The new file keeps the old one's permission bits, but not its owner or group, its ACLs, or its extended attributes such as Finder tags, and other hard links to the old file keep the old text. A save writes through a symlink to its target. A read-only file is refused. If the file changed on disk since the tab opened or last saved it, the save asks before it overwrites. If you cancel, the tab shows the ring, since its file no longer holds what the tab last read. **Save As** refuses a file that another tab has open.
- Closing a tab whose text differs from its file asks **Save**, **Don't Save**, or **Cancel**. Every tab's text, saved or not, comes back after you close the window or quit with `⌘Q`. At launch, a tab with no unsaved changes reloads its file if the file changed. A tab whose file was moved or deleted keeps its text, and its name is struck through until a save writes the file again.
- SQL Server runs native scripts in **Auto-commit**, including explicit `BEGIN TRANSACTION`, `COMMIT` and `ROLLBACK`. The toolbar reports when a transaction is open; its nesting depth and committability are unavailable through the SQL Server protocol. App-managed Manual mode is unavailable. Server-side code such as triggers can commit or replace a transaction, so the app cannot guarantee that wrapping an arbitrary batch keeps every write rollbackable.
- An error shows the available server diagnostics, including PostgreSQL SQLSTATE, and the editor underlines a reported error location.
- The **Output** button at the right end of the results header opens a timestamped log of everything the tab ran: each statement, its server messages such as `RAISE NOTICE` and warnings, and its result line. **Commit**, **Rollback**, and table edits are logged too. When a statement returns no rows, the log fills the results pane. The button turns amber when the latest run raised a warning.
- **Query history** groups identical SQL per connection and database. Search SQL, connection names, databases, or errors, then filter by **All**, **Failed**, or **Writes**. Select a query to preview its SQL and paged run timeline. Copy it, open or run it in a new tab on its saved database, or insert it into the active tab.
- **Saved queries** keeps the queries you use often. History pruning and **Clear history** never remove them. `⌘⇧E` saves the selection, or the marked statement, and asks for a name. A blank name uses the query's first comment, else its first 72 characters. **Save query** in query history saves the query you are previewing. Saving the same SQL again opens the entry you already have, marked **Already saved**. The bookmark button at the bottom of the sidebar, or `⌘E`, opens the list with the most recently used query first. Type to filter by name or SQL. `Enter` inserts the query at the active tab's cursor, or opens it in a new tab when no query tab is open. `⌘↵` opens it in a new tab, on the active tab's database when the dialects match, else on a connection of the query's dialect, else with no connection. `⌘C` copies it. **Edit** renames the query or changes its SQL, and **Delete** asks before it removes the query. A saved query holds up to 64 KB of SQL.

## Results and table data

- Drag a column's edge to resize it, or select a cell and press `⌥→` or `⌥←` to widen or narrow its column. The cell menu also sorts by the column and resets a resized width.
- Idle results show **Results appear here** and the run shortcut. The results header groups staged edits, result selection, status, and output and export controls. It wraps in narrow panes so those controls remain reachable. Long summaries show at most two lines, with the full text on hover. When a batch returns many results, its numbered selector scrolls horizontally.

- Import CSV into an existing PostgreSQL or supported SQL Server table from its context menu. Preview a prepared snapshot, choose a header, and map or skip fields. Unquoted empty fields become NULL, quoted empty fields stay empty text, and unmapped columns use defaults. Import shows byte progress and supports Cancel. PostgreSQL errors and cancellation roll back the import. PostgreSQL Manual mode keeps rows pending for Commit or Rollback. Production asks before importing on either database.
- SQL Server import requires Auto-commit and no open transaction. It locks the target table for the import, uses parameterized batches, preserves Unicode in `nchar`/`nvarchar`, and accepts ASCII only for `char`/`varchar`. Identity, computed, rowversion and generated columns cannot be mapped. Ordinary built-in defaults, checks and foreign keys still apply. Binary, legacy LOB, alias, CLR and encrypted columns cannot receive imported values. Enabled triggers, attached row-level security policies including disabled policies, indexed views, `IGNORE_DUP_KEY`, user-function expression dependencies, bound rules/defaults and special table kinds are unsupported. The initial metadata checks require SQL Server 2022 or later, database and target `VIEW DEFINITION`, `SELECT` on `sys.sql_expression_dependencies`, and `VIEW SECURITY DEFINITION` for users other than `dbo` or sysadmins. Such users are refused when database permissions contain `DENY VIEW DEFINITION` or `DENY CONTROL`, because hidden dependencies cannot be ruled out.
- SQL Server Cancel waits for the active batch to finish, then verifies rollback. If cleanup cannot finish within ten seconds after Cancel, or the connection fails during settlement, the session is retired and the app reports an unknown outcome. Check stored rows before retrying. Once commit starts, an acknowledged commit wins a late Cancel. A committed import stays committed if restoring session settings fails, and that session is retired. Rollback does not rewind identity or sequence allocations.
- SQL Server results preserve exact decimal and money values, Unicode, binary values, and temporal precision. A `sql_variant` shows the value it holds. A CLR value, such as a `hierarchyid`, `geography`, or `geometry`, shows as hexadecimal, so call its `.ToString()` in a query to read it as text. An `INSERT` export writes a `sql_variant` as text, so the value comes back with the base type `nvarchar`. Unsupported value conversions fail explicitly.
- SQL Server filters compare typed values and search the text shown in the grid. Equality filters for text, ntext, and XML compare serialized text. Text searches on floating-point columns or with excessively long patterns are refused with guidance.
- The results grid streams large results in pages. Select cells and press `⌘C` to copy them as TSV. Press `Enter`, or click the **…** on a cut-off value, to see the full value.
- Selecting two or more cells shows the count and the non-null count beside the status. A single integer or numeric column other than money also shows the exact sum, average, minimum, and maximum of the stored values. Money, text, and a rectangle of more than one column show the count only. Pending edits are not included and add the words `excludes pending edits`. A table page and a truncated result cover only the stored rows. To match a server sum over every row, raise **Row limit per result**, query that one column, and press `⌘A`.
- Right-click a foreign key cell, or press `⇧F10` on it, and choose **Go to referenced row in** the referenced table to open that table filtered to the row the key points at, with one filter per key column. When two keys from one cell reach the same table, each item names its key's columns. On PostgreSQL this works on any query whose key columns come straight from a table, and each copy of a key column follows its own row. On SQL Server it works on a table tab's own rows. A key with a `NULL` value cannot be followed. A key of several columns is not offered when the result shows a column of its table twice, as a self-join does, because the result cannot say which copy each column came from. A self-join that shows each key column only once can still mix two rows. If the referenced table already has a tab with no staged edits and its browse SQL unchanged, the follow replaces that tab's `WHERE`, `ORDER BY`, filters, and page. If that tab holds staged edits or edited SQL, the row opens in a second tab. The filter compares the text the grid shows, so a source session with a non-default `DateStyle`, `IntervalStyle`, or `extra_float_digits` can make a date, interval, or floating-point key find no row. The menu reads keys from the loaded catalog, as the primary key icons and staged edits do, so after schema changes made outside L1 Data, choose **Refresh catalog** in the connection's right-click menu before you follow a key.
- `⌘I`, or **View as record** in the grid's right-click menu, shows the selected row as a list of fields, each with its type glyph and its full value. It shows the saved values, not staged edits, and it is disabled on a staged new row. `↑` and `↓` move to the previous and next row.
- A run with several result sets has a selector to switch between them.
- **Export** writes a result as CSV, JSON, a Markdown table, or SQL `INSERT` statements. An `INSERT` export of one table keeps its identity values and leaves out computed columns, so the file replays into an empty copy of the table. Choose the loaded rows, or all rows when the grid holds only part of a read or one page of a table. All rows runs the statement again on the tab's own session, or reads the whole filtered table on a table tab, and streams every row to the file. On PostgreSQL the re-run happens in a read-only transaction that is always rolled back, so it cannot write or change your open transaction. A statement that may write offers only the loaded rows, and one that calls functions L1 Data cannot vouch for asks before it runs again. The results header shows the rows written so far, and **Cancel** or `Esc` stops the export. The file appears only when it is complete, so a cancelled or failed export leaves an existing file unchanged.
- A table tab pages through rows, from 10 to 1,000 per page. The pager follows the rows returned by the server, even when a row or size limit keeps fewer rows in the grid. The result status shows how many rows were kept. It filters with a `WHERE` condition or per-column filters, and sorts with `ORDER BY`. Click a header to sort by it, and Shift-click to add a column to the sort. From the keyboard, `⌥S` sorts by the selected cell's column and `⇧⌥S` adds it to the sort. SQL Server requires exact table column names for Shift-click sorting. If a raw name uses another spelling, edit `ORDER BY` or click without Shift to replace the simple column order.
- **Last page** fetches an exact filtered count. SQL Server counts use the table tab's session settings and include its uncommitted native writes. While SQL Server counts, the toolbar shows **Counting** and **Cancel**. **Cancel** or `Esc` resets that session. Page requests wait for the count, and the latest request wins. Changing the tab's target, query, text, or page intent while the count is pending discards the reply.
- A PostgreSQL table tab with a primary key can add, edit, and delete rows, and set a cell to `NULL` or `DEFAULT`. Changes stay pending until **Submit** (`⌘S`), which applies them in one transaction. In manual mode, submitted changes wait in the tab's open transaction until **Commit**. **Revert** asks, then drops them. If commit or rollback cannot be confirmed, the app asks you to verify saved data before retrying.
- SQL Server table results are read-only. Use SQL scripts to insert, update or delete rows. Staged grid writes are unavailable because server-side transaction control can defeat their all-or-nothing guarantee.

## The assistant

- SQL Server chats use the database's catalog and T-SQL context for suggestions. Model-written SQL cannot execute against SQL Server because it lacks the enforced read-only transaction used for PostgreSQL. Run a suggested SQL card in a normal query tab when you want to execute it.
- **Settings** > **General** sets assistant access across all chats. **Schema only** is the default. It sends database and schema structure, including table names, columns, types, and keys, and excludes editor SQL, errors, result rows, row estimates, and model queries. **Full access** also sends editor SQL and errors, enables result attachments, and allows read-only PostgreSQL queries under the chat's approval setting. Everything you type or paste into chat is sent in either mode. Switching access stops active turns and starts fresh provider context while keeping local history.
- The right panel is a chat with Claude. It runs on your own Claude subscription through the `claude` CLI you have installed and signed in to, so L1 Data needs no API key. Each message includes the active database and an outline of the schemas the sidebar shows. Full access adds the active tab's SQL, the statement at the cursor or selection, and the last error.
- On PostgreSQL, Claude reads the catalog through two tools that never ask. One describes tables, and the other searches table, column, and function names. In Full access, it can also run a read-only query. The permission picker under the message box chooses when a query asks first, and a change applies from the next query. In **Ask first**, every query waits for **Run** or **Deny**. In **Auto**, a query runs without asking only when it is a read whose every function call and operator is a vetted built-in: aggregates, window functions, math, string, date and time, JSON, array, and catalog helpers such as `pg_size_pretty`, and the comparison, arithmetic, text, pattern, JSON, and array operators. A query that calls any other function or operator, uses a `U&` escape, or selects `INTO` asks first and names what it found. Views, functions, and casts to or from types defined in the database are not inspected, so your database role is the last limit on what a query can reach. Only `SELECT`, `WITH`, `VALUES`, `TABLE`, `SHOW`, and `EXPLAIN` run. Each query runs on its own session in a `READ ONLY` transaction with a 30-second timeout, and Claude sees at most 50 rows.
- SQL in a reply shows as a card that names the tables it uses. **Run in new tab** opens the SQL in a new tab and runs it. **Insert at cursor** inserts it into the active tab. **Replace tab** replaces the active tab's text as one edit that `⌘Z` undoes. A card whose SQL writes, or calls a function the app cannot vouch for, offers **Open in new tab** in place of **Run in new tab**, so it waits for you to run it.
- In Full access, the paperclip attaches the result the active tab shows, up to 100 rows. Suggestion chips under a reply send their text as the next message. `Enter` sends, `Shift+Enter` starts a new line, and **Stop** ends the turn: it denies a waiting approval, asks the CLI to stop, and kills the process if it has not exited after 5 seconds. Quitting the app stops every turn the same way with a 1-second grace and kills any `claude` still running within about 4 seconds.
- The model and effort pickers list the models and effort levels your CLI offers. Switching models keeps the effort when the new model offers it. A new chat starts in **Ask first**, on the model and effort of your newest chat while the CLI still offers them. Chats are saved. A restart reopens the chat you had open, the history button lists the others, and the next message continues where the conversation left off. The history button shows a dot while a chat waits for your approval. If the CLI no longer has a chat's session, the next message restarts it with a summary of the conversation since the last access change and says so. Chats saved before access provenance was recorded start fresh. Deleting a chat asks first and removes it from L1 Data. The CLI keeps its own transcript of the conversation under its config directory, at `projects/<the app's assistant directory, with slashes as dashes>/<session id>.jsonl`.
- **Settings** > **Providers** shows the CLI's version, sign-in state, and plan, with a switch that turns the provider on or off. It also sets the display name, the binary path, the config directory, and the launch arguments. Launch arguments pass to the CLI, except the flags the app sets itself, which the field lists as ignored. `--model` and `--effort` there set the model and effort a new chat starts with. **Health check interval** under **Advanced** sets how often the app checks the CLI in the background. The default is 300 seconds, and 0 turns the check off.
- The **Usage** popup, opened by the chart button at the bottom of the sidebar, shows how much of each Claude subscription limit is left. Each window, such as the five-hour session or the week, gets a card with the percent left, a **Running low** warning, and the time until it resets. The app asks your own `claude` CLI for these numbers and reads no credentials itself. The refresh button at the top right reads them again, and the popup also reads them again when a window resets while it is open. If the CLI is not installed, the popup shows **not installed**. If it is signed out, the popup shows the command that signs it in.

## Updates

- L1 Data follows one of two update tracks, **Stable** or **Nightly**, which you choose in **Settings** > **General**. A build whose version contains `-nightly.` follows Nightly until you choose. The first launch saves that track, so a nightly install that the Nightly feed later moves onto a stable release stays on Nightly.
- The round button at the right end of the sidebar footer shows the update status. Click it to check for an update, click again to download what the check found, and click a third time to restart into the new build. A ring shows the download's progress, and a toast says when the download is ready. Nothing downloads without a click. Once a check finds a build, hovering the button lists what changed in it and in each release since the running build.
- Before the restart, a dialog names what the restart ends: running queries, open transactions, table edits that haven't been submitted, and assistant turns. If more starts before you confirm, the dialog opens again with the longer list. While the update installs, a notice covers the window and takes no input, so nothing new starts before the restart. If the install fails, the notice goes away and the button shows the error.
- The app checks 15 seconds after launch, then every 4 hours, and an hour after a failed check. Switching tracks checks at once. A nightly build on the Stable track is offered the latest stable release even when that release is older, so you can leave Nightly. Every other check offers only a newer build. The track cannot change while a download or an install runs.
- **Settings** > **General** shows the running version, the update status, and a button for the same next step as the sidebar button. Development builds, and Linux installs other than the AppImage, do not update themselves and show no sidebar button.

## The window

- **Settings** (`⌘,`) opens in a centered dialog over the dimmed, blurred workspace. It opens on **General**, which sets assistant access, the row limit, the table page size, and whether a script stops at its first error. General also shows the running version and update controls. Its section navigation and content scroll independently, and closing it returns focus to the control you left. **Appearance** picks a System, Light, or Dark scheme and the themes for each. It also sets the density (Compact, Standard, or Spacious), the speed of panel, dialog, and menu animations, Reduce motion (System, On, or Off), and the interface and monospace fonts and sizes. System follows the OS reduce-motion setting. With motion reduced, the side panels open without sliding, menus and dialogs fade in place, and pulsing indicators hold still. The monospace font is used by the SQL editor and the result tables. The search box above the sections filters the settings in place and shows the matches with their controls. `Esc` clears it and returns to the section you were on. With no search, `Esc` closes Settings.
- History, saved queries, connections, and theme dialogs share Settings' centered frame and blurred backdrop. `Esc` closes the active dialog first, after any field cancels its draft.
- On macOS the window keeps the native traffic lights. On Windows and Linux the app draws its own window controls and resize edges.

## Keyboard shortcuts

`Ctrl` works in place of `⌘` on Windows and Linux.

| Keys | Action |
|---|---|
| `⌘T` | New SQL tab |
| `⌘O` | Open `.sql` files |
| `⌘S` | Save the tab to its file, or submit pending table edits |
| `⌘⇧S` | Save the tab to a new file |
| `⌘N` | New connection |
| `⌘P` | Open quick navigation for databases, tabs, tables and views |
| `⌘⇧P` | Search available workspace commands |
| `⌘,` | Open or close Settings |
| `⌘W` | Close the tab, or close Settings |
| `⌘↵` | Run the selection, or the marked statement under the cursor |
| `⌘⇧↵` | Choose which statement to run, or all of them |
| `⌘⌥L` | Format the marked statement, or the statements the selection touches |
| `⌘E` | Open or close Saved queries |
| `⌘⇧E` | Save the selection, or the marked statement, to Saved queries |
| `Esc` | Cancel the running query |
| `Enter` | Edit the selected cell in an editable table, or show its full value elsewhere |
| `F2` | Edit the selected cell |
| `⌘⌫` | Delete or restore the selected rows |
| `⌘C` | Copy the selected cells as TSV |
| `⌘A` | Select all cells |
| `⌘I` | Show the selected row as a record |
| `⇧F10` | Open the selected cell's menu |

In query history, `↑` and `↓` select a query, `Enter` opens it in a new tab, `⌘↵` runs it in a new tab, and `Alt+Enter` inserts it at the active tab's cursor. `⌘C` copies the query unless text is selected in the search field. `Esc` closes history. **Clear history** asks for confirmation.

In Saved queries, `↑` and `↓` select a query, `Enter` inserts it at the active tab's cursor, `⌘↵` opens it in a new tab, and `⌘C` copies it unless text is selected in the search field. While you edit a query, `Enter` in the name field, or `⌘S` or `⌘↵` in the SQL, saves the edit. `Esc` leaves an edit or a confirmation first, and asks before it drops changed text. `Esc` from the list closes Saved queries.

On macOS, **Close Window** moves to `⇧⌘W` so that `⌘W` closes a tab. On macOS the global shortcuts take `⌘` only. `Ctrl` chords there stay with the editor.
